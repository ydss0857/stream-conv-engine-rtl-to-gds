4. Current diagnosis

In run v7, 20 paths violate at ss. 14 of them start at the reset input aresetn, which reaches the reset flops through a ~10-stage buffer tree (worst −2.27 ns). The worst path that does not start at reset misses by only −0.61 ns. Across a line-buffer width sweep, the non-reset slack degrades steadily as the flip-flop line-buffer array grows:

My reading is that two separate problems overlap:

  1. Reset distribution. A single synchronous reset from an input port must reach every reset flop (register-block reset values, valid bits, counters, FIFO pointers) within one cycle, after a 2.5 ns input delay. At ss the buffer tree cannot do this.
  2. The flip-flop line-buffer array. The window generator's read address and enables fan out across the whole array every cycle. I suspect, but have not yet confirmed net by net, that these nets account for most of the ~9,000 slew violations at ss (the worst violators are inserted fanout buffers with ~2.07 ns input transitions). This path dominates as the array grows. Placing and repairing at the ss corner (v7) improved total slack but left the slew-violation count essentially unchanged.

The faster hs library closes the logic paths to −0.75 ns (75 MHz, enough for 720p60), at +33% area and 2.2× power.

5. What I plan to try next

  1. Registered, replicated reset: register aresetn at the boundary and give each block its own local reset flop. Also remove resets from flops that don't need one.
  2. Line-buffer read path: bank the line buffers and register the bank select and decoded address one cycle early, so no read-address net spans the array.
  3. SRAM line buffers using sky130's OpenRAM 1rw1r macros. By macro dimensions, two 1 KB macros match the flip-flop cell area at about 440 pixels of width. The PDK only provides a typical-corner model for them, though.
  4. Repair settings in small steps (slew margin 20 → 30%, wire-length buffering), after v4 showed that large jumps do not converge.

6. Questions

  1. Reset: for a hardened macro like this, what reset style would you recommend: a registered and replicated synchronous reset, asynchronous assert with synchronous deassert, or treating reset as a multicycle or false path?
  2. Flip-flop memories: for a ~2,000-bit flip-flop array read every cycle, is banking with a pipelined read the usual fix, or would you go straight to SRAM (given the typical-only macro model in sky130)?
  3. Slew violations: why might sizing buffers for the ss corner leave ~9,000 max-slew violations essentially unchanged? Is this a sign that something in my setup (constraints or floorplan) is wrong?
  4. Sign-off target: LibreLane's default sky130 sign-off checks setup only at the typical corner. For an academic project, is it reasonable to sign off at tt and report the ss Fmax, or should I keep pushing for all-corner closure?
